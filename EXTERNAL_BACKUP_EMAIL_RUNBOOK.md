# Внешний backup и email-оповещения — подготовка

Проверка 3 ноября 2026. До обновления квоты пользователь запретил переключение VM.

## Фактическое состояние

Bucket `tradingbot-paper-backup-101494113814-ew1`: `europe-west1`, Standard,
uniform bucket-level access включён, public access prevention `enforced`.
Анонимное перечисление объектов вернуло HTTP 401. Прямых `allUsers` и
`allAuthenticatedUsers` в политиках bucket и проекта не найдено. Проверка не
охватывает все возможные IAM deny и групповые назначения; bucket пуст, поэтому
анонимное чтение конкретного объекта не проверялось. Public access prevention
блокирует публичные разрешения независимо от наличия публичных IAM bindings.
https://cloud.google.com/storage/docs/public-access-prevention

Для uploader service account на bucket назначены `roles/storage.objectCreator`
и `roles/storage.objectViewer`; прямых назначений в политике проекта и
скачиваемых пользовательских ключей нет. Bucket policy не показывает все
унаследованные разрешения. Прямая проверка действующих разрешений от имени SA
не удалась: оператору не разрешено impersonation. Запись и чтение от VM ещё не
подтверждены. Не расширять роли без конкретного диагностированного недостатка.

Создан один включённый email-канал Cloud Monitoring на согласованный владельцем
адрес. Адрес и ID не сохраняются в Git. К каналу не привязано alert policy,
verification status API не определён, доставка владельцу не проверена. Сам по
себе канал не обнаруживает остановку. Внешней копии и мониторинга ещё нет.

## Минимальный вариант мониторинга

VM раз в 5 минут публикует скалярную custom metric на `resource.type=global`.
Политика отсутствия точки 15 минут отправляет email при открытии и закрытии
инцидента. Пример выключенной политики с placeholder ID канала —
`deploy/monitoring-heartbeat-policy.template.json`; publisher, descriptor,
policy и разрешение `monitoring.timeSeries.create` ещё не созданы. Перед их
созданием проверить минимальную роль и назначить только необходимый доступ.

Google предупреждает, что metric-absence по выключенному ресурсу VM может не
работать; применение `global` — предложение, которое необходимо проверить на
реальной остановке. Без первой полученной точки отсутствие может не вызвать
инцидент. `CLOSED` может означать авто-закрытие, а не восстановление: его надо
сверять со свежей положительной точкой. К 15 минутам прибавляются задержки
сбора и доставки. Email не зависит от Telegram-поллера и не требует открытия
публичного административного порта.

Источники: https://cloud.google.com/monitoring/alerts/metric-absence ;
https://cloud.google.com/monitoring/alerts/troubleshoot-missing-notifications ;
https://cloud.google.com/monitoring/api/ref_v3/rest/v3/projects.alertPolicies .

При 30 днях и одной scalar-точке раз в 5 минут: 8640 × 8 байт = 69120 байт,
примерно 0,0659 MiB/месяц. Без остатка бесплатной квоты и при $0,258/MiB это
около **$0,017/месяц**; первые 150 MiB метрик общие для billing account, его
остаток неизвестен. Запись Monitoring API отдельно не тарифицируется; начало
тарификации alerting объявлено не раньше сентября 2027. Этот вариант не требует
Pub/Sub, Cloud Run или Secret Manager. Тарифы и объём логов могут измениться.
https://cloud.google.com/products/observability/pricing

При предыдущем замере сжатого архива 309394 байта оценка хранения, загрузок и
read-back с семидневным soft delete — около $0,0054/месяц. Вместе с оценкой
метрики без учёта её бесплатной квоты — около $0,0224/месяц. Налоги, внешний
egress, дополнительные запросы, рост БД и фактический счёт проекта не включены;
общий предел $15 не доказан. Подробные допущения — PAPER_RESILIENCE.md.

## Процедура после обновления квоты

Окно остановки ранее разрешено; до обновления квоты не начинать переключение.
Перед началом заново проверить код, силы и время для восстановления, паузы,
позиции, долги, funding, команды, журналы, настройки, цены и защитные циклы.
Не закрывать позиции. При ошибке, неизвестной позиции, неполных funding/учёте,
нехватке времени или непроверенной процедуре остановиться до выключения.

1. Через штатное `/pause_all` дождаться подтверждения всех рынков и убедиться,
   что защита позиций работает. Сохранить исходные паузы. Создать согласованный
   backup financial/queue/observation через `tradingbot-paper-backup.service`,
   проверить SHA-256, integrity/FK и восстановить отдельную копию для сверки
   журнала, позиций, долгов, funding и очереди без запуска приложений. Если
   проверка не проходит, сохранить паузу, продолжить защиту и не выключать VM.
2. Остановить нужные службы корректно, убедиться в отсутствии вторых писателей
   и поллеров и снять второй согласованный backup. Окно без защиты фиксировать.
   Остановить VM и прикрепить существующий SA без создания ключей:

```bash
gcloud compute instances stop tradingbot-paper-test --project=gen-lang-client-0854183882 --zone=europe-west1-b
gcloud compute instances set-service-account tradingbot-paper-test \
  --project=gen-lang-client-0854183882 --zone=europe-west1-b \
  --service-account=tradingbot-backup-uploader@gen-lang-client-0854183882.iam.gserviceaccount.com \
  --scopes=cloud-platform
gcloud compute instances start tradingbot-paper-test --project=gen-lang-client-0854183882 --zone=europe-west1-b
```

   При ошибке определить реальный статус VM/SA read-only, не повторять вслепую;
   безопасно вернуть действующие службы на паузе. Если SSH/запуск недоступны,
   сохранить копии и сообщить конкретную ошибку.
3. После запуска проверить, что все службы на паузе; сверить позиции, funding,
   долги, журнал, настройки, котировки, защиту и единственность поллера. Для
   Spot/isolated отдельная метка защитной проверки пока не реализована: свежая
   цена сама её не доказывает. При расхождении или непроверенном риске оставить
   входы на паузе, не заменять живую базу старым снимком.
4. Проверить доступ SA и сделать первую часовую копию из проверенного checkout:

```bash
cd /opt/trading-bot-diagnostics-a41ac38
sudo -u tradingbot env HOME=/var/lib/tradingbot \
  python3 -B deploy/paper_external_backup.py \
  --bucket tradingbot-paper-backup-101494113814-ew1 --kind hourly
```

   Скрипт создаёт согласованный SQLite backup, проверяет локальное
   восстановление, загружает с create-only условием, считывает объект назад и
   записывает marker только после совпадения SHA-256. Затем скачать именно этот
   объект в новый приватный каталог и независимо вызвать `inspect_restore`,
   сверив журнал, капитал по одинаковым ценам, позиции, долги, funding и
   очередь. При ошибке прав/сети/hash/данных не считать внешний backup готовым,
   не включать таймеры и не добавлять права вслепую. Сохранить объект и данные.
5. Лишь после успешного реального восстановления установить и проверить
   подготовленные hourly/daily timers и marker возраста. Подготовить heartbeat
   и политику из шаблона, проверить реальные остановку и восстановление и
   получение владельцем обоих email. Перезапуск может потребовать отдельного
   безопасного окна; отсутствие уведомления — не подтверждение здоровья.
6. Возобновить только те Spot/isolated входы, которые были разрешены и прошли
   проверки. Margin и cross оставить на паузе. После новых финансовых событий
   старую базу поверх текущей не восстанавливать: сначала сохранить и сверить
   новые проводки. Обновить HANDOFF и ROADMAP фактическими результатами.
