# Offline inbox/outbox — этап 2, блок 5

Экспериментальный автономный прототип. Он **не подключён** к Telegram, рабочему
боту, `Engine`, `Store`, журналу ордеров или восстановлению этапа 4. Не использует
сеть, токен, chat ID, имена пользователей или raw-сообщения. `Update` и `ResponseSimulator`
работают только с синтетическими значениями во временных отдельных базах SQLite.
Не используйте этот код для реальной торговли без отдельной интеграции и проверки.

## Контракт

- Получатель передаёт строго упорядоченный, полный пакет нормализованных synthetic
  updates. Проверка Telegram-подписи/пользователя и получение пакета не реализованы:
  `authorized` — только результат внешней проверки в тестовой фикстуре, не защита.
- Одна транзакция записывает весь пакет inbox и `next_offset`. Только после commit
  вызывающая сторона вправе подтверждать все полученные updates; сам прототип не
  вызывает Telegram API. Неавторизованное обновление хранится без команды/данных.
- Повтор того же update ID с тем же содержимым — no-op; другой payload и ранее
  невиденный ID ниже offset отклоняются. Это консервативная политика для стенда;
  реальные правила Telegram, в том числе смену последовательности ID после простоя,
  до интеграции нужно отдельно обработать. Доказательство полноты сетевого ответа
  и безопасное подтверждение через `getUpdates` ещё не реализованы.
- Worker выбирает минимальный pending update под `BEGIN IMMEDIATE`. Транзакция
  одновременно фиксирует тестовый эффект, DONE и одно ответное сообщение outbox.
  Падение до commit откатывает все три; после commit повтор не выполняет команду.
- Реализованы только синтетические команды PAUSE/STOP/RESUME и CLOSE для локальной
  тестовой модели. CLOSE закреплён за внутренним `(position, version)`: повторные
  разные updates создают максимум одно closing intent, а старый target не действует
  на новую версию. Это тестовая запись, а не торговый ордер и не интеграция с Engine.
  Остальные реальные команды, политика TTL и safety gates ещё не реализованы.
- Outbox независимо фиксирует PENDING → SENDING → SENT. Ошибка или падение после
  отправки оставляет SENDING; повторная отправка **может продублировать уведомление**,
  но не вызывает worker команды. `requeue_uncertain` допустим только после того,
  как внешняя процедура гарантировала отсутствие другого активного sender. Сам
  прототип не реализует lease/fencing sender и не обещает exactly-once уведомления.
- Уникальность эффектов привязана к сохранности одной SQLite и использованию данного
  API. Разные базы, прямой SQL, внешний side effect внутри транзакции или неверно
  назначенная версия позиции в неё не входят. База создана отдельно, текущая рабочая
  БД отклоняется как чужая; миграции и интеграции с другими блоками нет.

## Проверка

```sh
python -B -m unittest discover -s tests -p test_telegram_inbox.py -v
python -B -m unittest discover -s tests -v  # полная регрессия в Linux
```

11 новых тестов, полный Linux-набор 119 тестов. Тесты создают отдельные временные
БД и не требуют сети или Telegram. Проверены транзакции и настоящие `os._exit`
до и после commits при приёме, применении команды, захвате и сохранении ответа;
конкурирующие workers, дубли updates и close-target, timeout после отправки,
неавторизованный update и защита от чужой БД. Тесты не доказывают безопасность
сетевого адаптера, выбора target, фактической авторизации или взаимодействия с биржей.
