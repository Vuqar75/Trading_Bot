# Запускаемое приложение BTCUSDT Spot

Новая точка входа: `python3 -m trading_bot.app`. Это отдельное приложение,
не изменение `python3 -m trading_bot` и не развёртывание старого бота.
Стратегия SMA 10/30 доступна, но её прибыльность не подтверждена.
По умолчанию paper, 15m, 10 USDT на вход, пауза при каждом запуске.
15m — настраиваемая исходная гипотеза, не результат оптимизации или рекомендация.

## 1. Проверка без аккаунтов и сети

Из корня этой ветки, Python 3.12+, Linux:

```bash
python3 -B -m trading_bot.app --demo
python3 -B -m unittest discover -s tests -v
```

Демо использует временную базу, не читает переменные секретов и не отправляет запросы.
Ожидается: 2 ордера, позиция 0, net_pnl 0.0859000, pending 0.

## 2. Paper с публичными котировками Testnet

Без Telegram и без входов (диагностика подключения):

```bash
python3 -B -m trading_bot.app --mode paper --once --db data/new-runtime-paper.db
```

При ошибке данных --once возвращает код 1, пишет безопасный runtime-health.json.
Постоянный режим: убрать --once. Для управления через Telegram нужны переменные
RUNTIME_TELEGRAM_BOT_TOKEN и RUNTIME_TELEGRAM_OWNER_ID в окружении и флаг --telegram.
Используйте ОТДЕЛЬНОГО Telegram-бота: второй polling-процесс с токеном старого бота
нарушит его работу. Личную конфигурацию старого launcher приложение не читает.
Не сохраняйте действующие значения в Git, чат, командную историю или отчёты.
Пример только с пустыми значениями: deploy/runtime.env.example.

```bash
python3 -B -m trading_bot.app --mode paper --db data/new-runtime-paper.db --telegram
```

Команды: /status, /signal, /history, /pause, /stop, /resume, /close.
/stop и /pause запрещают входы, не останавливают процесс и защиту позиции.
/close ставит паузу и сохраняет запрос для текущей позиции, не обещает исполнение.
/resume и /close старше запуска процесса или 120 секунд не исполняются.
Пауза не отменяет уже начатую отправку. Ответы могут дублироваться после сетевого
сбоя, торговое действие из-за повтора ответа не повторяется.

Таймфреймы: --interval 1m|5m|15m|1h. Смена режима, размера входа или таймфрейма
требует отдельной БД. Интервал опроса --poll-seconds (по умолчанию 10, минимум 5).

## 3. Spot Testnet, отдельные тестовые ключи

Только виртуальные средства Binance Spot Testnet; production URL отсутствует.
Нужны BINANCE_TESTNET_API_KEY и BINANCE_TESTNET_API_SECRET в защищённом окружении.
Для первого прогона используйте выделенный Testnet-аккаунт без других торговых
процессов, внешних ордеров и ручных изменений BTC. Старую рабочую БД не использовать.

```bash
python3 -B -m trading_bot.app --mode testnet --enable-testnet-orders \
  --db data/new-runtime-testnet.db --interval 15m --telegram
```

Флаг разрешает возможность отправки только на Testnet; входы всё равно на паузе
до новой команды /resume после старта. Максимум настроенного входа 10 USDT,
одна принадлежащая приложению Spot-позиция. SELL может закрыть весь её торгуемый
остаток, не ограничиваясь 10 USDT. Плеча, margin, futures и production здесь нет.
Наличие флага не означает, что сетевой прогон уже проверен.

В текущем облачном окружении публичный Testnet возвращает HTTP 451. Реальный
биржевой прогон НЕ выполнен. Не заменяйте Testnet на production для обхода ошибки.
Проверяйте официальную доступность сервиса для среды запуска. Если API недоступен,
приложение остаётся на паузе, сетевые ордера не проверяются.

## Устройство и гарантии

- Одна SQLite-база, dedicated schema, FULL synchronous. Старые Store/journal/inbox
  не мигрируются и не используются. Режим и fingerprint API-ключа привязаны к БД.
- Один процесс на канонический путь БД через flock. Несколько машин/разных БД с
  одним аккаунтом не поддерживаются: это не распределённый fencing.
- Намерение и clientOrderId сохраняются до отправки. Claim фиксируется отдельно
  перед единственной POST-попыткой. После исключения — UNKNOWN, только GET-сверка.
- PREPARED, оставшийся после перезапуска до claim, истекает без автоматической
  отправки. SUBMITTING/UNKNOWN/ACK сверяются до новых действий.
- Полученный POST-ответ не используется как доказательство settlement: GET order,
  страницы myTrades и повторный GET order проверяются по identity и итогам.
- Cumulative fills совпадают с executedQty/cummulativeQuoteQty. Ранее учтённые fills
  не исчезают и не изменяются. Новые fills, позиция, деньги и уведомление — один commit.
- Все fills сохраняют комиссию и актив. BTC/USDT учитываются; сторонняя комиссия
  остаётся неоценённой. Числовой PnL тогда предварительный, помечен неизвестным;
  следующие входы заблокированы. Стоимость стороннего актива не считается нулевой.
- Размер проверяется по LOT_SIZE, MARKET_LOT_SIZE и min/max notional. Это проверка
  по ticker, не гарантия биржевого принятия: рынок и средняя цена фильтра меняются.
- Остаток после округления не забывается. Dust ниже фильтра остаётся в позиции;
  входы не возобновляются автоматически. Нет автоматической конвертации dust.
- При старте ручная пауза всегда включена. Дневной лимит реализованного убытка
  5 USDT UTC; открытый убыток этим лимитом не ограничивается. Виртуальная стратегия
  имеет внутренний бюджет 1000 USDT; в Testnet дополнительно проверяются free assets.
- Программные stop/take: 2%/4% относительно средней себестоимости с известными
  входными комиссиями. Работают на паузе, по ticker до загрузки свечей. Это НЕ
  биржевые защитные ордера: сеть, API, процесс или неизвестный ордер задерживают выход.
- Сетевые операции идут вне SQLite-транзакций. Telegram-приём атомарно фиксирует
  команду/запрос действия/ответ/offset. При DB-сбое следующие updates не принимаются.
- Telegram идентификатор проверяется из from.id и private chat.id, не из текста.
  Sender ID и токен не записываются в БД; сохраняется только результат авторизации.
  Протокол допускает разреженные update_id, без пропуска незафиксированных updates.

## Что ещё НЕ доказано и чего не делать

Тесты проверяют API-контракт на имитаторе, не сервер Binance. Не выполнены реальные
ордерные прогоны, cancel API, account-wide история, User Data Stream, автоматическое
восстановление после Testnet reset, сторонняя оценка комиссий, futures/margin,
аппаратный power-loss и независимое ревью новой реализации. Наблюдение известных
client IDs не доказывает отсутствие внешних исполнений в истории аккаунта.

При not-found или недоступном API автоматической переотправки и снятия UNKNOWN нет.
При подтверждённом REJECTED включается ORDER_REJECTED_REVIEW и пауза: автоматического
retry и снятия блокировки нет; нужна отдельная процедура расследования. При противоречии
учёта включается устойчивая ACCOUNTING_CONTRADICTION; ручного «сбросить вслепую» нет.
Для исправления требуется расследование и отдельная процедура, не SQL-удаление gate.
Не запускать с реальными средствами. Не выдавать это за завершённый multi-market бот.

## Постоянный сервер

VM не создана. Для Linux VM подготовлены deploy/trading-bot-paper.service и backup
service/timer. Порядок установки под администратором (после выбора проекта/стоимости):

1. Python 3.12+, системный пользователь/group tradingbot; git checkout фиксированного
   проверенного коммита в /opt/trading-bot, root-owned/read-only для сервиса.
2. /etc/trading-bot/runtime.env, root:root 600 с ОТДЕЛЬНЫМ Telegram-ботом.
   systemd читает файл до снижения прав. Не source непроверенных файлов в shell.
3. Скопировать paper.service, backup.service и backup.timer в /etc/systemd/system.
4. systemctl daemon-reload; systemctl enable --now trading-bot-paper.service.
   Приложение стартует на паузе; проверить /status и журнал до /resume.
5. systemctl enable --now trading-bot-backup.timer.
6. journalctl -u trading-bot-paper.service, статус systemd и возраст файла
   /var/lib/trading-bot-runtime/runtime-health.json. Проверять error, blocked,
   telegram_error и возраст quote.time, не только живой процесс.

Последний snapshot: /var/lib/trading-bot-backups/latest.db. SQLite backup API
делает согласованный снимок, затем integrity_check и atomic rename. Для настоящей
эксплуатации нужны ротация/копии вне VM и отдельный внешний мониторинг с оповещением.
Часовой latest.db на том же диске не защищает от потери VM/диска.

```bash
python3 -B -m trading_bot.runtime_backup data/new-runtime-paper.db /tmp/runtime-backup.db
```

Восстановление старой копии после уже исполненных ордеров может терять новые
clientOrderId: НЕЛЬЗЯ просто восстановить backup и возобновить торговлю. Требуется
дополнительная сверка биржевой истории. Для paper это виртуальные деньги.

systemd restart не обеспечивает непрерывность при недоступности API и не заменяет
защитные ордера, мониторинг или восстановление состояния. Telegram может задержать
следующий цикл на сетевые тайм-ауты: опрос 10 секунд не является жёсткой гарантией.
