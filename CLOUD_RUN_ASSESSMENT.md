# Cloud Run assistentstpb и применимость к Trading_Bot

Проверка выполнена только для чтения; настройки ресурсов, запущенные процессы и
секреты не изменялись. Значения секретов, Telegram ID и личная конфигурация не
запрашивались. Это срез конфигурации на момент проверки, не мониторинг доступности.

## Что обнаружено

- Доступен проект Google Cloud `assistentstpb-cloud-run`; `assistentstpb` также
  существует как отдельный приватный GitHub-репозиторий. Попытка обратиться к
  Google Cloud проекту с ID `assistentstpb` получила PERMISSION_DENIED: нельзя
  заключить, существует ли он или у текущей учётной записи нет доступа.
- В первом проекте найден **Cloud Run service** `bot`, регион `us-central1`,
  активная ревизия `bot-00004-5fh`, 100% трафика на неё. Контейнер создан из
  source deploy и опубликован в Artifact Registry. Это HTTP-сервис, не VM и не
  Cloud Run Job или worker pool. Сервисный ingress открыт; IAM допускает allUsers.
- Dockerfile развёрнутого снимка запускает Python 3.13 и Functions Framework:
  `functions-framework --target bot --source main.py --port 8080`. На уровне
  Cloud Run command/args не переопределены. Код приложения содержит HTTP-функцию
  `bot`, создающую Telegram Application, разбирающую HTTP-тело в Update и вызывающую
  `process_update`: это обработчик **webhook**. В доступном исходном коде не найден
  polling/getUpdates. Фактическая регистрация webhook в Telegram отдельно не
  проверялась: токен и личные настройки не запрашивались.
- В просмотренном снимке и текущей main-ветке репозитория совпадают Dockerfile и
  requirements по Git blob SHA, но `main.py` отличается. Вывод о работающей ревизии
  основан на архиве исходников конкретного развёртывания, не на предположении о
  текущем GitHub HEAD. Не извлекались или не просматривались таблицы, `.env`,
  пользовательские данные и секреты из архива.
- Заданы 1 vCPU, 512 MiB памяти, concurrency 80 запросов на экземпляр, timeout
  300 секунд; startup CPU boost включён. Максимум 20 экземпляров. Явный minimum
  instances отсутствует; для стандартного автомасштабирования действует значение
  по умолчанию 0. CPU throttling/billing не переопределён: согласно документации
  Cloud Run по умолчанию применяется request-based billing и CPU выделяется при
  обработке запросов, запуске и остановке. Это вывод из отсутствия переопределения,
  а не измерение фактической загрузки CPU.
- Приложение загружает Excel-файл, включённый в образ, в process-local `dataframes`.
  Комментарий о Firebase Storage не подтверждается просмотренной реализацией
  загрузки: там `pandas.read_excel`/`ExcelFile` читает локальный файл. Кэш отдельный
  для каждого экземпляра и пропадает при его замене; постоянная БД или подключённый
  том в конфигурации сервиса не обнаружены. Значения файла не читались.
- Cloud Run управляет жизненным циклом экземпляров. При отсутствии запросов сервис
  может уменьшиться до нуля; новый запрос может запустить контейнер. Экземпляры могут
  завершаться и заменяться в процессе эксплуатации, включая аварии или обслуживание;
  нет основания утверждать непрерывный немедленный перезапуск того же процесса или
  сохранение его локальных файлов. Фактические события перезапуска и логи с
  пользовательским содержимым не анализировались.

## Оценка для Trading_Bot

**Текущий шаблон непригоден без архитектурных изменений** для непрерывного торгового
цикла и единственной SQLite: без запросов CPU доступен не постоянно и возможен ноль
экземпляров; при нагрузке возможно несколько независимых циклов; локальная база
контейнера не является постоянным общим хранилищем. Лимит max=1 сам по себе не
заменяет надёжную межпроцессную блокировку или восстановление после обрыва. SQLite
WAL не рассчитан на совместный доступ нескольких хостов через сетевую файловую
систему; просто вынести его в общий сетевой каталог — не доказанное решение.

| Вопрос | Изменённый Cloud Run | Небольшая стандартная VM |
|---|---|---|
| Цикл | Выделенный worker pool/подходящий long-lived ресурс либо instance-based CPU + минимум экземпляров, с учётом прерываний; webhook по необходимости отделить от worker. Проверить доступность и стоимость выбранного ресурса. | Отдельный процесс под systemd, автоматический старт и рестарт после сбоя; настроить health checks и оповещения. |
| Хранение | Внешняя транзакционная БД, миграции, резервные копии и проверка восстановления; распределённая аренда/защита единственного исполнителя и fencing. | Один writer SQLite на устойчивом Persistent Disk, транзакции и корректные SQLite backup/snapshot с проверкой восстановления. Диск не защищает сам от всех сбоев и ошибок. |
| Сбои | Надёжные intent/fill ledger, повторная сверка после старта, дедупликация и обработка неизвестных исходов; нельзя полагаться на локальную память или штатное завершение. | Те же журнал, дедупликация и сверка. systemd/automatic restart не гарантируют отсутствие пропусков или дублей и не заменяют контроль позиции. |
| Масштабирование | Больше управляемой инфраструктуры, но сложнее гарантировать единственного исполнителя и консистентное состояние. | Простой singleton для первой пары и SQLite; обслуживание ОС, патчи, резервирование и наблюдаемость — ответственность владельца. |
| Расходы | Зависит от выбранного режима CPU, минимума экземпляров, БД и трафика. | Постоянные расходы на VM и диск даже без сделок; точная сумма зависит от региона, типа и диска. |

Для текущего исследовательского масштаба предпочтительна **небольшая стандартная VM
с Persistent Disk**, отдельным системным пользователем, минимальными правами,
systemd, проверяемыми резервными копиями и наблюдаемостью. Не использовать Spot VM
как основу непрерывного исполнения без отдельного анализа прерываний. Даже тогда
перед автоматической торговлей нужно завершить и независимо проверить интеграцию
надёжного исполнения, startup reconciliation, защиту позиции и защиту от повторных
команд; текущие исследовательские модули offline не доказывают готовность торгового
контура. Переход, подключение Testnet, развёртывание, возобновление paper-бота и
реальные средства требуют отдельных указаний пользователя.
